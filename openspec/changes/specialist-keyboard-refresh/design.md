## Context

Reply-клавиатура специалиста (`build_main_keyboard`) — постоянная клавиатура, привязанная к чату на стороне Telegram. Жёсткий конструктив платформы: **обновить reply-клавиатуру можно только новым сообщением** с актуальным `reply_markup`; `editMessageReplyMarkup` работает лишь для inline-кнопок. Сейчас свежая клавиатура отправляется только в `_consume_and_reply` при успешном `/start <token>` (`src/bot/handlers/start.py`), поэтому после добавления кнопок специалист вынужден повторно вводить токен.

Узнавание уже привязанных пользователей в коде есть: `SqlAlchemySpecialistsRepo.find_by_chat_id`. Для клиентов столбец `clients.telegram_chat_id` хранится, но метода `find_by_chat_id` нет.

Стартовая точка бота — `src/__main__.py::main` (long-polling), диспетчер собирается в `src/bot/dispatcher.py::build_dispatcher`.

## Goals / Non-Goals

**Goals:**
- После деплоя, изменившего набор кнопок, специалист видит новую клавиатуру **без** повторного `/start <token>` и **без** единого лишнего сообщения от бота.
- Голый `/start` без токена перестаёт грубить уже привязанным специалисту/клиенту.
- Минимальный диф, без новых внешних зависимостей.

**Non-Goals:**
- Бродкаст-пинг «меню обновлено» на старте бота (вариант D1) — сознательно отвергнут ради «ноль лишних сообщений».
- Перенос меню в `setMyCommands` / inline (вариант C).
- Reply-клавиатура для клиента — у клиента кнопок нет, его это не касается.
- Журналирование сообщений специалисту через client-audit — запрещено правилом `bot.md`.

## Decisions

### 1. Версия клавиатуры = хеш подписей кнопок (не ручной счётчик)
`keyboard_version(messages) -> str` считает стабильный хеш по упорядоченному списку подписей кнопок `build_main_keyboard`. Добавил/переименовал кнопку → версия меняется сама.
- **Почему хеш, а не int-счётчик:** счётчик надо вручную бумпать при каждом изменении меню — легко забыть, рассинхрон. Хеш не требует человеческого шага и не врёт.
- **Альтернатива (отвергнута):** хранить весь JSON клавиатуры — избыточно; для сравнения достаточно короткого хеша.

### 2. Хранение версии — столбец `specialists.keyboard_version` (nullable)
Сравнение «доставленная клиенту версия vs текущая» на специалиста. `NULL` ⇒ ещё не доставляли (мигрированные/старые записи) ⇒ при первом же действии получат свежую клавиатуру и версию.
- Миграция добавляет nullable-столбец без backfill — `NULL` корректно трактуется как «устарело».

### 3. Механика D3 — outer-middleware, piggyback на исходящем ответе
Outer-middleware в `bot/`:
1. По входящему апдейту достаёт `chat_id`, ищет специалиста (`find_by_chat_id`).
2. Если специалист найден и `stored != current_hash` — помечает контекст «нужно подложить клавиатуру» и **после** обработки хендлером гарантирует, что отправленный ответ несёт `reply_markup=build_main_keyboard`, затем пишет `keyboard_version = current_hash`.
- **Почему outer-middleware, а не правка каждого хендлера:** централизованно, хендлеры не знают про версии; один источник истины.
- **Подкладывание `reply_markup`:** ответ специалисту бот шлёт почти всегда; middleware либо инжектит markup в исходящий вызов, либо (если хендлер по сценарию ничего не ответил) обновление откладывается до следующего действия — лишнего сообщения не создаём.
- **Bump только после успешной отправки:** версию фиксируем, лишь когда свежая клавиатура реально ушла, иначе при сбое доставки потеряем обновление.

### 4. Голый `/start` (вариант A) — ручной немедленный выход
Ветка `if not token:` в `make_start_handler`:
- спец по `chat_id` → `[start].already_welcomed` + `build_main_keyboard`, фиксируем версию;
- иначе клиент по `chat_id` → новый текст `[start].already_linked` (клиентский, без клавиатуры);
- иначе → `[start].no_token` (как сейчас).

Порядок: спец → клиент → никто. Роли на одном аккаунте сосуществуют (см. `clients` спеку), но для голого `/start` приоритет у роли специалиста — у него есть клавиатура, которую и надо обновить.

## Risks / Trade-offs

- **Кнопки появляются не в секунду деплоя, а при первом действии специалиста** → для ежедневно работающего офиса это «в первый же заход сегодня»; голый `/start` даёт мгновенный ручной выход. Приемлемо.
- **Middleware на каждом апдитете делает лишний запрос `find_by_chat_id`** → нагрузка ничтожна (единицы специалистов); при желании можно кешировать, но YAGNI.
- **Гонка двойного обновления (middleware + голый `/start` в одном апдейте)** → `/start` сам бампит версию; middleware, увидев уже совпавшую версию, ничего не делает. Идемпотентно.
- **Сбой доставки ответа** → версию не бампим, обновление повторится при следующем действии.

## Migration Plan

1. Миграция: `ALTER TABLE specialists ADD COLUMN keyboard_version VARCHAR NULL` (Alembic).
2. Деплой кода. Существующие специалисты имеют `keyboard_version = NULL` ⇒ при первом действии получают свежую клавиатуру и версию — это и есть желаемое обновление после релиза.
3. Откат: удалить middleware и столбец; поведение возвращается к «обновление только через `/start <token>`». Данные не теряются.
