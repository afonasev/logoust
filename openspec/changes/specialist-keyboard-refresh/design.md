## Context

Telegram принимает в `sendMessage.reply_markup` один вид разметки: постоянную клавиатуру либо inline-кнопки. Обновить постоянную клавиатуру через редактирование сообщения нельзя. Поэтому сохранить inline-сценарий и обновить меню одним и тем же сообщением невозможно.

## Goals / Non-Goals

- Узнавать подключённых пользователей по голому `/start`.
- Обновлять меню без повторного приглашения и без дополнительных сообщений.
- Сохранять существующие inline-сценарии и полный аудит клиентских отправок.
- Не включать отложенный прокси в эту реализацию.

## Decisions

### Версия и хранение

Версия — стабильный хеш упорядоченных подписей основной клавиатуры. Nullable-столбец `specialists.keyboard_version` хранит последнюю доставленную версию. Миграция `0017` добавляет поле без backfill; старые записи получают NULL.

### Исходящий middleware сессии

`KeyboardRefreshMiddleware` подключён к сессии Bot в `src/__main__.py`. Для `SendMessage` без разметки сверяет версию специалиста и отправляет копию запроса со свежей клавиатурой. Исходный запрос остаётся пригодным для повторной попытки после ошибки. Версия сохраняется только после успешной отправки. Сообщения клиентов, неизвестных адресатов, запросы по username и редактирования не получают клавиатуру.

Ответы со своей разметкой пропускаются. Обновление ждёт следующей подходящей отправки, включая фоновое сообщение специалисту. Отдельных сообщений нет. Ручной выход — `/start`, всегда отправляющий актуальную клавиатуру. Явная доставка клавиатуры при онбординге также сохраняет версию после успеха.

### Узнавание и аудит

Порядок ролей для голого `/start`: специалист, затем клиент, затем неизвестный пользователь. Специалист получает `already_welcomed` с клавиатурой, клиент — `already_linked`, неизвестный — `no_token`. Новые записи не создаются.

Подтверждение клиенту журналируется через единую воронку как `connection_confirmed`, с полным текстом и статусом sent/failed; ошибки TelegramForbiddenError/TelegramBadRequest сохраняются в аудите. При нескольких карточках одного аккаунта выбирается минимальный id, остальные не меняются. Сообщения специалисту в клиентский аудит не попадают.

## Risks / Trade-offs

- При работе только с inline-ответами меню автоматически не обновится; `/start` даёт немедленное обновление без токена.
- Несколько одновременных отправок могут доставить одну версию повторно; дополнительных сообщений middleware не создаёт.
- Каждая подходящая отправка проверяет специалиста в БД; кеш не нужен при текущем объёме.

## Migration Plan

1. Применить `0017` при отдельной разрешённой выкладке.
2. Запустить код: старые версии обновляются при подходящих отправках или `/start`.
3. При откате сначала вернуть старый код, затем при необходимости откатить миграцию. Клиентские данные не меняются.
